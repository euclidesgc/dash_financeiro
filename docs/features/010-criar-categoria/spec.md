# SPEC 010 — criar categoria

Décima fatia da SPA. Página nova "Categorias" (`/app/categories`), ligada no cabeçalho ao lado de "Saldos" e "Gastos", onde o dono vê o catálogo inteiro (rótulo, quantos gastos usam, se é do sistema ou dele), cria uma categoria pelo rótulo, renomeia qualquer uma inline e apaga as que criou e ninguém usa. Para isso a fatia **resolve a dívida 023**: o rótulo em pt-BR sai de `app/taxonomy/seed.json` e passa a viver na coluna `categories.label`; toda leitura de rótulo do painel React (`GET /api/categories`, lista de gastos, "Por categoria", ordenação por categoria) passa a vir do banco por `JOIN`, e o `CASE … WHEN` gerado em Python some.

O que o código já faz hoje, e que esta SPEC reaproveita:

- `app/migrations/sql/012_taxonomy_tree.sql` · `categories (id, name TEXT UNIQUE, group_id NOT NULL REFERENCES category_groups)`. Sem `label`, sem `is_system`. Última migração: `019_category_manual.sql`; `NUMBERING.md` diz que a próxima é `020`. O aplicador (`app/migrations/runner.py`) só executa `.sql`, uma transação por arquivo.
- `app/taxonomy/seed.py` · `load_seed()`, `UNCATEGORISED = "Não classificado"`, `Category(key, label)`, `category_labels()` (dict do seed), `label_sort_key()`, `pickable_categories()` (seed, sem `UNCATEGORISED`, ordenado por rótulo), `seed_taxonomy(conn)` — reconcilia grupos, regras e `categories` (`INSERT … ON CONFLICT (name) DO UPDATE SET group_id = excluded.group_id`) e dá `commit`. É chamado pela CLI, por `scripts/e2e-backend.sh` e por 40 testes; **não** roda no boot do app.
- `app/taxonomy/classify.py:_record_categories` · a cada `classify_all`, insere em `categories` (`ON CONFLICT DO NOTHING`, grupo de fallback) toda categoria observada em `transactions.category` — uma categoria pode existir na tabela sem estar no seed.
- `app/routers/spending.py:52` e `app/routers/rules.py:25` · `LABELS: dict[str, str] = category_labels()` **no import do módulo**, sem conexão (telas Jinja). `tests/test_taxonomy_tree.py:36-38` e `tests/test_gastos_screen.py:181` comparam com `category_labels()`.

## Decisões técnicas

### D1 — Migração `020_category_labels.sql`: `label` e `is_system` em `categories`, preenchidos a partir do seed no próprio SQL

- Escolha: `ALTER TABLE categories ADD COLUMN label TEXT NOT NULL DEFAULT ''; ALTER TABLE categories ADD COLUMN is_system INTEGER NOT NULL DEFAULT 1;` seguido de **77 linhas literais** `UPDATE categories SET label = '<rótulo>' WHERE name = '<chave>';` (uma por entrada de `seed.json` em 23/09/2026, geradas uma vez e congeladas — migração é histórico, não lê arquivo) e, por último, `UPDATE categories SET label = name WHERE label = '';` para categoria observada pela ingestão que não está no seed. Base nova: a tabela está vazia, os `UPDATE`s não fazem nada e `seed_taxonomy` grava o rótulo ao inserir. Base do dono: as 77 linhas já existem (registradas por `classify_all` depois da reconciliação da `012`) e saem da migração com rótulo, sem depender de a CLI de seed rodar. `is_system` fica `1` para tudo que existe e para o que a ingestão registra; só `create_category` grava `0`.
- Alternativa descartada: coluna `created_at` — motivo: nenhum requisito a lê e nenhuma tela a mostra; coluna sem leitor é estrutura ociosa (norma 12: pendência vai para o roadmap, não para o esquema).
- Alternativa descartada: migração só com os `ALTER` e backfill em `seed_taxonomy` — motivo: o app não roda o seed no boot; a base do dono mostraria chave em inglês até alguém lembrar de `python -m app.taxonomy.seed`. O rótulo é parte do esquema que a fatia 009 já lê em requisição; tem de chegar com a migração.
- Alternativa descartada: `label` nulo (`TEXT`) com `COALESCE(label, name)` em todo leitor — motivo: espalha a regra por seis consultas; com `NOT NULL DEFAULT ''` e o `UPDATE` final, a invariante "toda linha tem rótulo" vale a partir da migração, e `_record_categories` passa a gravar `label = name` para mantê-la.
- Alternativa descartada: índice único em `fold(label)` — motivo: índice sobre função Python registrada por conexão quebra qualquer ferramenta que abra o arquivo sem `connect()` (o próprio `sqlite3` da linha de comando). A unicidade sem caixa/acento é checada em `catalogue.py` com `SELECT … WHERE fold(label) = fold(?)`, dentro da mesma transação da escrita.

### D2 — O seed insere o que falta e não sobrescreve rótulo renomeado

- Escolha: em `seed_taxonomy`, o upsert de `categories` vira `INSERT INTO categories (name, group_id, label) VALUES (?, ?, ?) ON CONFLICT (name) DO UPDATE SET group_id = excluded.group_id, label = CASE WHEN categories.label IN ('', categories.name) THEN excluded.label ELSE categories.label END`. Rótulo igual à chave significa "ninguém deu nome ainda" (foi `_record_categories` ou o `UPDATE` final da `020`); qualquer outro valor é do dono ou do seed anterior e fica. `category_labels()` do seed passa a chamar-se `seed_labels()` (dict do arquivo): continua alimentando `LABELS` dos routers Jinja no import (não há conexão ali) e o teste da árvore. `pickable_categories(conn)` passa a ler `SELECT name, label, is_system FROM categories WHERE name != ? ORDER BY fold(label), name`. `label_sort_key` é removido (o `ORDER BY fold()` faz o mesmo em SQL; `fold` e `label_sort_key` coincidem para todo rótulo do seed). `_record_categories` grava `(name, group_id, label = name)`.
- Alternativa descartada: `category_labels(conn)` lendo o banco — motivo: depois do `JOIN` (D3) nenhum leitor do painel precisa de um dict; criar a função seria criar o que não se usa. Os routers Jinja continuam no seed por decisão (ver "Dívida").
- Alternativa descartada: seed nunca tocar `label` em conflito — motivo: uma categoria registrada pela ingestão **antes** do seed (`label = name`, ex.: "Groceries") nunca ganharia "Supermercado". O `CASE` cobre esse caso; o custo é o único edge em que o dono renomeia uma categoria exatamente para a chave dela (o seed seguinte devolve o rótulo do arquivo).

### D3 — Rótulo por `JOIN` em `app/queries/expenses.py` e `app/queries/categories.py`; o `CASE` gerado some

- Escolha: `_FROM` ganha `LEFT JOIN categories AS c ON c.name = t.category`; constante `_LABEL = "COALESCE(c.label, NULLIF(t.category, ''))"` (categoria fora da tabela aparece pela chave, como hoje — `test_expenses_api.py:412` continua valendo); `_SELECT` traz `{_LABEL} AS category_label`; `_item(row, names)` lê `row["category_label"]` e perde o parâmetro `categories`; `_SORT_SQL["category"]` vira `"CASE WHEN {_LABEL} IS NULL THEN 1 ELSE 0 END, fold({_LABEL}) {order}, t.category"`; `_category_rank_clause` e `_page_sql`'s `order_params` somem; `_BY_CATEGORY` seleciona `{_LABEL} AS label` (coluna determinada pela chave do `GROUP BY`, permitido pelo SQLite) e `sum_by_category` usa `row["label"]` (ou "Sem categoria" para nulo). `expenses.py` deixa de importar `seed.py`. Módulo novo `app/queries/categories.py`: `CategoryRow(key, label, is_system: bool, usage_count: int)` e `list_categories(conn) -> list[CategoryRow]` = `SELECT c.name, c.label, c.is_system, count(t.id) AS usage_count FROM categories AS c LEFT JOIN transactions AS t ON t.category = c.name WHERE c.name != ? GROUP BY c.id ORDER BY fold(c.label), c.name`, e `get_category(conn, key) -> CategoryRow | None` (mesma forma, `WHERE c.name = ?`). `usage_count` conta **todo lançamento** com a chave, não só gasto: apagar uma categoria que uma transferência ainda usa deixaria chave órfã; para categoria criada pelo dono, que só recebe ajuste manual pela página de gastos, os dois números coincidem.
- Alternativa descartada: manter o `CASE` gerado e ler `category_labels(conn)` — motivo: é exatamente a dívida 023; a fatia existe para fechá-la.
- Alternativa descartada: `ORDER BY c.label COLLATE NOCASE` — motivo: `NOCASE` do SQLite só dobra ASCII; "Água" iria depois de "Z". `fold` já existe em toda conexão.

### D4 — Escrita em `app/taxonomy/catalogue.py`; router traduz para 201/200/204, 403, 404, 409, 422

- Escolha: módulo novo `app/taxonomy/catalogue.py` com `InvalidLabelError(ValueError)`, `DuplicateLabelError(ValueError)`, `CategoryNotFoundError(LookupError)`, `SystemCategoryError(PermissionError)`, `CategoryInUseError(RuntimeError)` (atributo `usage_count`); `slugify(label) -> str` (`fold` → só `[a-z0-9]`, runs viram `-`, bordas sem `-`; vazio vira `categoria`); `_unique_key(conn, base)` acrescenta `-2`, `-3`… enquanto `name` existir; `_check_label(conn, label, except_key=None)` faz `strip`, vazio → `InvalidLabelError`, `SELECT 1 FROM categories WHERE fold(label) = fold(?) AND name != ?` → `DuplicateLabelError`; `create_category(conn, label) -> str` (chave) insere com `group_id` do grupo `is_fallback = 1`, `is_system = 0`, e `commit`; `rename_category(conn, key, label)` exige `key != UNCATEGORISED` e existente (`CategoryNotFoundError`), `UPDATE categories SET label = ?`, `commit`; `delete_category(conn, key)`: não existe → `CategoryNotFoundError`; `is_system = 1` → `SystemCategoryError`; `count(*) FROM transactions WHERE category = ?` > 0 → `CategoryInUseError(n)`; senão `DELETE`, `commit`. Nenhuma chamada a `classify_all`: criar/renomear/apagar não muda `transactions`. `app/routers/categories.py` ganha `CategoryOut { key, label, is_system: bool, usage_count: int }`, `CategoryInput { label: str }`, `connect()` em `try/finally`, e os handlers `POST ""` (201, devolve `get_category`), `PATCH "/{key}"` (200), `DELETE "/{key}"` (204) mapeando: `InvalidLabelError` → 422 "Informe o nome da categoria."; `DuplicateLabelError` → 422 "Já existe uma categoria com esse nome."; `CategoryNotFoundError` → 404 "Categoria não encontrada."; `SystemCategoryError` → 403 "Categoria do sistema não pode ser apagada."; `CategoryInUseError` → 409 "Esta categoria está em uso por N gasto(s)." (singular/plural resolvido no servidor: "1 gasto", "3 gastos"). `override.set_manual` passa a validar contra `{c.key for c in pickable_categories(conn)}`.
- Alternativa descartada: `detail` estruturado `{ message, usage_count }` no 409 — motivo: `ApiError.detail` é `string` e `readDetail` descarta objeto; o front já tem `usage_count` na lista (R9 não precisa chamar a API para explicar). O número vai no texto.
- Alternativa descartada: chave = o próprio rótulo — motivo: renomear mudaria a chave e desligaria os lançamentos; a chave é estável e o rótulo é dado.
- Alternativa descartada: escrita em `app/queries/categories.py` — motivo: `queries/` é leitura (norma 33); escrita com regra de domínio fica no domínio `taxonomy`, ao lado de `override.py` e `rules.py`.

### D5 — Contrato JSON

- `GET /api/categories` · 200 `{ "categories": [ { "key": "Food and drinks", "label": "Alimentação", "is_system": true, "usage_count": 12 }, { "key": "pet-shop", "label": "Pet shop", "is_system": false, "usage_count": 0 }, … ] }`, ordenado por `fold(label)`; nunca contém `"Não classificado"`.
- `POST /api/categories` · body `{ "label": "Pet shop" }` → 201 `{ "key": "pet-shop", "label": "Pet shop", "is_system": false, "usage_count": 0 }`; 422 `{ "detail": "Informe o nome da categoria." }` (vazio ou só espaços); 422 `{ "detail": "Já existe uma categoria com esse nome." }` (`fold` igual a qualquer rótulo existente, inclusive "Sem categoria"); 422 do Pydantic se faltar `label`.
- `PATCH /api/categories/{key}` · body `{ "label": "Mercado" }` → 200 com o item atualizado; 404 `{ "detail": "Categoria não encontrada." }` (chave inexistente ou `"Não classificado"`); 422 como no `POST`, ignorando a própria chave (renomear "Pet shop" para "PET SHOP" é aceito).
- `DELETE /api/categories/{key}` · 204 sem corpo; 404; 403 `{ "detail": "Categoria do sistema não pode ser apagada." }`; 409 `{ "detail": "Esta categoria está em uso por 3 gastos." }`.
- `GET /api/transactions/expenses`, `/by-category` e `PATCH /api/transactions/{id}/category` · mesmo contrato; `category` (rótulo) passa a refletir o rótulo do banco.
- Sem sessão → 401 em todos (`test_route_guard` varre as rotas novas sozinho).

## Dívida encontrada

- **Telas Jinja ficam no seed.** `app/routers/spending.py` e `app/routers/rules.py` montam `LABELS` no import do módulo, sem conexão; passam a usar `seed_labels()` e **não** veem rótulo renomeado nem categoria criada pelo dono. Fechar exige ler `categories` em requisição nessas duas telas (e em `tests/test_gastos_screen.py`). Item de roadmap: `jinja-labels-from-schema`, depende desta fatia.
- **Duas chamadas ao mesmo endpoint.** `src/features/expenses/api/get-categories.ts` e `src/features/categories/api/get-categories.ts` buscam `GET /api/categories` com a mesma chave `['categories']`; pela regra "usado por duas features → compartilhado" (`project-structure`), o hook e o tipo deveriam ir para `src/hooks/` e `src/types/`. Decisão do dono para esta fatia; item de roadmap: `shared-categories-query`.
- Rotas do SPA não usam `lazy` nem `getHref` (skill `routing`); as quatro rotas seguem o mesmo padrão direto. Item de roadmap só se o bundle passar a pesar.
- `usage_count` conta todo lançamento com a chave, mas a tela diz "gastos"; para categoria do dono os números coincidem hoje (só a página de gastos atribui categoria manualmente). Se uma fatia futura permitir categorizar transferência, o texto precisa mudar ou a contagem filtrar por `SPENDING`.
- Dívida 025 inalterada (`get_expense` sem `SPENDING`, predicado em dois lugares); a precedência de regra por descrição sobre categoria manual no `group_id` (registrada na SPEC 009) continua.
